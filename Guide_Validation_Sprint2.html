1 Architecture Microservices

L'architecture est basée sur Spring Cloud. Chaque service est indépendant, avec sa propre base de données. Ils communiquent via l'API Gateway (point d'entrée unique) et OpenFeign (appels directs entre services).

Pourquoi utiliser une API Gateway ?
Pour avoir un seul point d'entrée. Le frontend n'a pas besoin de connaître l'adresse de chaque service — il appelle toujours localhost:8080. La Gateway route ensuite la requête vers le bon service. Elle gère aussi le CORS de façon centralisée.
Qu'est-ce qu'Eureka Server ?
C'est le registre de services (Service Discovery). Chaque microservice s'enregistre sur Eureka au démarrage avec son nom et son adresse. Quand le Retake Service appelle "claim-service" via Feign, Eureka lui donne l'adresse réelle automatiquement — pas besoin d'hardcoder les URLs.
Pourquoi chaque service a sa propre base de données ?
C'est le principe du découplage en microservices. Chaque service est maître de ses données. On ne peut pas faire de JOIN SQL entre deux bases différentes — c'est pour ça que retakeRequestId dans Claim est un simple Long (référence cross-service) et non une relation JPA.

Règles métier — createClaim()

Règle 1 : Anti-doublon
Si un étudiant essaie de créer une réclamation avec le même sujet et qu'il a déjà une réclamation active (OPEN ou IN_PROGRESS) sur ce sujet → on lance une DuplicateClaimException. ClaimService — backend/claim-service/src/main/java/tn/english/school/claimservice/service/ClaimService.java 
boolean isDuplicate = claimRepository.existsByStudentIdAndSubjectAndStatusIn(
    claim.getStudent().getId(),
    claim.getSubject(),
    List.of(ClaimStatus.OPEN, ClaimStatus.IN_PROGRESS)
);
if (isDuplicate) {
    throw new DuplicateClaimException("Duplicate Alert: ...");
}
Pourquoi ? Pour éviter le spam et les réclamations en double.
Règle 2 : Le statut initial est toujours OPEN
Peu importe ce que le frontend envoie, le service force status = OPEN à la création. ClaimService — backend/claim-service/src/main/java/tn/english/school/claimservice/service/ClaimService.java 
claim.setStatus(ClaimStatus.OPEN); // Forcé par le service
return claimRepository.save(claim);
Pourquoi ? On ne fait jamais confiance aux données du client pour les champs critiques.
Règle 3 : Upsert de l'étudiant
L'étudiant est sauvegardé/mis-à-jour localement dans claim_db. Le claim-service maintient une copie locale des données utilisateur pour éviter les appels réseau constants vers auth-service.

Règles métier — updateClaim() et deleteClaim()

if (existing.getStatus() != ClaimStatus.OPEN) {

}

La logique est similaire : on protège les réclamations en cours de traitement contre toute modification ou suppression accidentelle.

Règles métier — authorizeRetake() Logique avancée

C'est la règle la plus complexe — explique-la bien !
  1. Vérification du type : Seules les réclamations de type PEDAGOGICAL peuvent être autorisées en rattrapage. Une réclamation TECHNICAL ne peut pas générer un rattrapage.
  2. Vérification du statut : Si la réclamation est déjà RESOLVED ou CANCELED, on refuse (claim fermée).
  3. Idempotence : Si c'est déjà RETAKE_AUTHORIZED, on retourne simplement l'existant sans sauvegarder à nouveau.
  4. Changement de statut : On passe à RETAKE_AUTHORIZED.
ClaimService — backend/claim-service/src/main/java/tn/english/school/claimservice/service/ClaimService.java 
public Claim authorizeRetake(Long id) {
    Claim existing = getClaimById(id);

    // Règle 1 : Uniquement les claims pédagogiques
    if (existing.getType() != ClaimType.PEDAGOGICAL) {
        throw new IllegalStateException("Only pedagogical claims can be authorized for a retake.");
    }
    // Règle 2 : Pas si la claim est fermée
    if (existing.getStatus() == ClaimStatus.RESOLVED || existing.getStatus() == ClaimStatus.CANCELED) {
        throw new IllegalStateException("Cannot authorize a retake for a closed or canceled claim.");
    }
    // Règle 3 : Idempotence — si déjà autorisé, ne pas re-sauvegarder
    if (existing.getStatus() == ClaimStatus.RETAKE_AUTHORIZED) {
        return existing;
    }

    existing.setStatus(ClaimStatus.RETAKE_AUTHORIZED);
    return claimRepository.save(existing);
}

4 Communication Inter-Services — OpenFeign

OpenFeign permet à un microservice d'appeler un autre microservice comme si c'était une simple méthode Java, sans écrire du code HTTP manuel.

Pourquoi OpenFeign ici ?

Quand un étudiant soumet une RetakeRequest, le Retake Service doit vérifier l'état de la Claim correspondante (statut, type) — données qui se trouvent dans le Claim Service.

Au lieu de dupliquer les données ou de faire une requête HTTP manuelle, on utilise OpenFeign pour appeler l'API du Claim Service directement depuis le code Java du Retake Service.

Interface ClaimClient — dans le Retake Service

ClaimClient — backend/retake-service/src/main/java/tn/english/school/retakeservice/client/ClaimClient.java 
@FeignClient(name = "claim-service")  // "claim-service" = nom enregistré sur Eureka
public interface ClaimClient {

    @GetMapping("/api/claims/{id}")
    ClaimDTO getClaimById(@PathVariable("id") Long id);

    @PutMapping("/api/claims/{claimId}/link-retake/{retakeRequestId}")
    ClaimDTO linkRetakeRequest(
        @PathVariable("claimId") Long claimId,
        @PathVariable("retakeRequestId") Long retakeRequestId
    );
}

Ce qui se passe quand on appelle claimClient.getClaimById(1L)

1
Le code Java appelle claimClient.getClaimById(1L) — comme une méthode normale
2
Feign interroge Eureka pour trouver l'adresse réelle de "claim-service"
3
Feign construit automatiquement une requête HTTP GET vers http://localhost:8081/api/claims/1
4
Feign désérialise la réponse JSON en objet ClaimDTO et le retourne
Comment fonctionne OpenFeign ? Qu'est-ce qui se passe en coulisses ?
1. Le Retake Service démarre et s'enregistre sur Eureka.
2. Quand il appelle claimClient.getClaimById(1L), Feign interroge Eureka pour trouver l'adresse de "claim-service".
3. Feign construit automatiquement la requête HTTP GET vers http://localhost:8081/api/claims/1.
4. Il désérialise la réponse JSON en objet ClaimDTO.
Pourquoi utiliser ClaimDTO et pas l'entité Claim directement ?
Parce que le Retake Service ne dépend pas du code du Claim Service. Le DTO est une copie locale des champs nécessaires. Cela respecte le principe de découplage — chaque microservice est indépendant.
Où Feign est-il utilisé concrètement dans le Retake Service ?
Dans RetakeRequestService, à trois endroits :
1. createRetakeFromClaim() → vérifie le type et le statut de la Claim avant de créer, puis appelle linkRetakeRequest() pour enregistrer le lien dans le Claim Service.
2. updateRequest() → vérifie que la Claim est encore OPEN avant d'autoriser la modification.
3. deleteRequest() → vérifie que la Claim est encore OPEN avant de supprimer.

ClaimDTO (dans retake-service)

ClaimDTO — backend/retake-service/src/main/java/tn/english/school/retakeservice/dto/ClaimDTO.java 
public class ClaimDTO {
    private Long id;
    private String status;    // "OPEN", "RETAKE_AUTHORIZED", etc.
    private String type;      // "PEDAGOGICAL", "TECHNICAL", etc.

}

5 Sécurité JWT

Connais les grandes lignes, tu n'as pas codé l'auth-service — mais tu dois savoir comment ton module s'en sert.

Comment ça marche (à expliquer en 3 phrases)

  1. Login : L'utilisateur envoie email/password → auth-service vérifie et génère un token JWT (chaîne encodée contenant : userId, email, role, expiration).
  2. Stockage : Angular stocke le token dans le localStorage.
  3. Appels sécurisés : À chaque requête, Angular ajoute automatiquement Authorization: Bearer <token> grâce au tokenInterceptor. Le backend valide le token.

Rôles dans le projet

RôlePeut faire
STUDENTCréer une réclamation, voir ses propres réclamations, envoyer des messages, soumettre une RetakeRequest
ADMINVoir toutes les réclamations, changer les statuts, autoriser les rattrapages, approuver/refuser les RetakeRequests, voir la colonne ML Analysis

Intercepteurs Angular

tokenInterceptor
Ajoute automatiquement le header Authorization: Bearer <token> sur tous les appels vers l'API Gateway (:8080).
errorInterceptor
Intercepte les erreurs 401 (non authentifié) et 403 (non autorisé) et redirige vers la page de login.
Qu'est-ce qu'un JWT ? Que contient-il ?
JWT = JSON Web Token. C'est une chaîne encodée en base64 composée de 3 parties séparées par des points : Header (algorithme) + Payload (données : userId, email, role, expiration) + Signature (pour vérifier l'authenticité). Il est stateless — le serveur n'a pas besoin de stocker de session.
Comment sécurises-tu tes endpoints ?
Dans la configuration Spring Security, les endpoints publics (login, register) sont autorisés sans token. Les autres requièrent un JWT valide. Au niveau du frontend, le tokenInterceptor injecte le token sur chaque requête, et l'errorInterceptor redirige si le token est expiré ou invalide (401/403).

6 Tests Unitaires — JUnit + Mockito TRES IMPORTANT

Le prof a insisté : les tests ne doivent pas se limiter au CRUD simple. Tu as des tests de logique métier complexe. Connais-les parfaitement !

Concept clé : Tests Unitaires vs Tests d'Intégration

Tests Unitaires (ClaimServiceTest)

- Testent une seule classe isolément
- Utilisent des mocks (faux objets) à la place des vraies dépendances
- Rapides, pas de base de données
- @ExtendWith(MockitoExtension.class)
Tests d'Intégration (ClaimServiceIntegrationTest)

- Testent le système complet (service + repository + base de données)
- Utilisent une vraie base H2 en mémoire
- Plus lents, mais vérifient la vraie intégration
- @SpringBootTest

Annotations Mockito à connaître

AnnotationRôleExemple
@MockCrée un faux objet@Mock ClaimRepository claimRepository;
@InjectMocksInjecte les mocks dans la classe testée@InjectMocks ClaimService claimService;
when(...).thenReturn(...)Définit ce que le mock doit retournerwhen(repo.findById(1L)).thenReturn(Optional.of(claim));

Test 1 — Création réussie (cas normal)

@Test
void createClaim_success() {
    // ARRANGE : préparer les mocks
    when(userRepository.findById(1L)).thenReturn(Optional.of(student));
    when(userRepository.save(any(User.class))).thenReturn(student);

        1L, "Exam contestation", List.of(OPEN, IN_PROGRESS)
    )).thenReturn(false);  // Pas de doublon

    verify(claimRepository).save(claim);  // Vérifier que save a été appelé
}
Remarque le pattern AAA : Arrange / Act / Assert. C'est la structure standard d'un bon test unitaire.

ClaimService Angular — le pont entre UI et API

C'est le service central du frontend. Il regroupe TOUS les appels HTTP vers le Claim Service ET le Retake Service. Les composants injectent ce service et ne font jamais d'appels HTTP directement.
ClaimService — frontend/src/app/routes/claims/services/claim.service.ts 
@Injectable({ providedIn: 'root' })
export class ClaimService {
  private readonly http = inject(HttpClient);
  private readonly claimApi = environment.claimApiUrl;   // http://localhost:8080/api
  private readonly retakeApi = environment.retakeApiUrl;  // http://localhost:8080/api

  // Retourne toutes les claims (ADMIN) ou celles d'un étudiant (filtre par studentId)
  getAllClaims(studentId?: number) {
    const url = studentId
      ? `${this.claimApi}/claims?studentId=${studentId}`
      : `${this.claimApi}/claims`;
    return this.http.get<Claim[]>(url);
  }

  authorizeRetake(id: number) {
    return this.http.patch<Claim>(`${this.claimApi}/claims/${id}/authorize-retake`, {});
  }

  createRetakeFromClaim(claimId: number, courseName: string, reason: string, file: File) {
    const formData = new FormData();
    formData.append('retakeRequest', new Blob([JSON.stringify({ courseName, reason })], { type: 'application/json' }));
    formData.append('attachment', file);
    return this.http.post(`${this.retakeApi}/retake-requests/from-claim/${claimId}`, formData);
  }
}

export function tokenInterceptor(req: HttpRequest<unknown>, next: HttpHandlerFn) {
  const tokenService = inject(TokenService);

  // Si le token est valide, on l'ajoute sur toutes les requêtes
  if (tokenService.valid() && shouldAppendToken(req.url)) {
    return next(
      req.clone({
        headers: req.headers.append('Authorization', tokenService.getBearerToken()),
      })
    ).pipe(
      catchError((error: HttpErrorResponse) => {
        if (error.status === 401) tokenService.clear();  // Token expiré
        return throwError(() => error);
      })
    );
  }
  return next(req);
}

10 Questions-Réponses pour la Soutenance

Prépare-toi à expliquer chaque réponse avec tes propres mots, sans lire ce guide.

Architecture

Pourquoi avoir séparé Claims et Retakes en deux services différents ?
Parce qu'ils ont des responsabilités différentes. Le Claim Service gère le processus de réclamation (communication student-admin). Le Retake Service gère la logique administrative du rattrapage (document, approbation). En les séparant, chaque service peut évoluer indépendamment, et si le Retake Service tombe, les réclamations continuent de fonctionner.
Comment les deux services communiquent-ils ?
Via OpenFeign. Le Retake Service déclare une interface ClaimClient annotée @FeignClient(name="claim-service"). Feign interroge Eureka pour trouver l'adresse du Claim Service, puis construit automatiquement les requêtes HTTP. Quand une RetakeRequest est créée, Feign appelle linkRetakeRequest() pour que le Claim Service enregistre le lien de son côté.
Qu'est-ce que le Service Discovery et pourquoi c'est utile ?
Eureka Server est le Service Discovery. Chaque microservice s'y enregistre au démarrage. Au lieu d'hardcoder "http://localhost:8081" dans le code, on utilise juste le nom logique "claim-service" et Eureka résout l'adresse réelle dynamiquement. C'est utile si un service change de port ou d'adresse.

Tests

Quelle est la différence entre @Mock et @Autowired dans les tests ?
@Mock crée un faux objet simulé (mock) qui ne fait rien par défaut — on lui dit ce qu'il doit retourner avec when(...).thenReturn(...). C'est pour les tests unitaires où on veut isoler la classe testée. @Autowired injecte un vrai objet du contexte Spring — c'est pour les tests d'intégration avec @SpringBootTest.
Pourquoi utiliser @Transactional dans les tests d'intégration ?
Pour isoler les tests. Avec @Transactional, toutes les modifications de base de données effectuées dans un test sont automatiquement annulées (rollback) à la fin du test. Ainsi, chaque test repart d'un état propre et les tests n'interfèrent pas entre eux.
Pourquoi faire claimRepository.flush() dans le test anti-doublon ?
Hibernate est lazy — il met les opérations en file d'attente et ne les exécute pas forcément immédiatement. Sans flush(), le premier INSERT est dans le cache de la session mais pas encore dans la vraie table SQL. Le flush() force l'écriture physique en base de données, pour que la requête existsByStudentIdAndSubjectAndStatusIn qui vérifie le doublon lise les données réelles.
Pourquoi verify(claimRepository, never()).save(any()) est important ?
Ce n'est pas suffisant de vérifier qu'une exception est lancée. Il faut aussi vérifier que le code s'est bien arrêté avant de sauvegarder. Sans ce verify, on ne sait pas si les données corrompues ont quand même été enregistrées en base avant que l'exception soit lancée.

Logique métier

Pourquoi retakeRequestId est un Long et pas une relation JPA @ManyToOne ?
Parce que RetakeRequest est dans une base de données séparée (retake_db). JPA ne peut pas faire de JOIN entre deux bases de données différentes. On stocke juste l'ID numérique comme référence cross-service. Si on veut les données complètes, on fait un appel REST/Feign vers le Retake Service.
Qu'est-ce que l'idempotence ? Donne un exemple dans ton code.
L'idempotence signifie qu'appeler la même opération plusieurs fois produit le même résultat sans effets secondaires supplémentaires. Dans authorizeRetake(), si le statut est déjà RETAKE_AUTHORIZED, on retourne simplement l'objet existant sans appeler claimRepository.save(). Ainsi, autoriser un rattrapage deux fois est équivalent à l'autoriser une fois.
Pourquoi l'étudiant est-il dupliqué dans claim_db ?
C'est un pattern appelé "local copy" ou "data denormalization". Le Claim Service maintient une copie locale des données utilisateur pour éviter un appel réseau vers auth-service à chaque lecture. Le service fait un "upsert" (insert ou update) au moment de la création d'une réclamation pour maintenir les données synchronisées.

@Service
public class HuggingFaceService {

    // Ligne 1 : @Value injecte la valeur de "groq.api.token" depuis application.properties
    // GROQ est une API compatible OpenAI qui donne accès à des LLMs ultra-rapides (ex: LLaMA)
    @Value("${groq.api.token:}")           // ":}" = chaîne vide si variable absente (pas de crash)
    private String apiToken;

    // URL du endpoint GROQ — format identique à l'API OpenAI (compatible)
    private static final String GROQ_API_URL = "https://api.groq.com/openai/v1/chat/completions";

    // Modèle LLM utilisé : LLaMA 3.3 70B — très performant pour la rédaction
    private static final String MODEL = "llama-3.3-70b-versatile";

    // RestTemplate = client HTTP synchrone de Spring pour faire des appels REST
    private final RestTemplate restTemplate = new RestTemplate();

    public String draftAdminResponse(Claim claim) {
        try {
            // Ligne A : Création des headers HTTP
            HttpHeaders headers = new HttpHeaders();

            // Ligne B : Authorization Bearer = standard pour les API modernes
            // Le token GROQ s'obtient sur console.groq.com
            headers.set("Authorization", "Bearer " + apiToken);
            headers.set("Content-Type", "application/json");
            headers.set("Accept", "application/json");

            // Ligne C : Corps de la requête — format OpenAI Chat Completions
            Map<String, Object> body = Map.of(
                "model", MODEL,                    // Quel LLM utiliser
                "messages", List.of(
                    Map.of("role", "system", "content",
                        "You are a professional academic administrator. "
                        + "Write concise, empathetic responses to student claims. "
                        + "Keep responses to 2-3 sentences. No greetings or sign-offs."),
                    // Message "system" = instructions globales données au modèle

                    Map.of("role", "user", "content",
                        String.format(
                            "Write a professional administrator response to this student claim:\n\n"
                            + "Subject: %s\nType: %s\nDescription: %s",
                            claim.getSubject(), claim.getType(), claim.getDescription()
                        ))
                    // Message "user" = la vraie demande avec les données de la réclamation
                ),
                "max_tokens", 150,          // Limite la longueur de la réponse
                "temperature", 0.7          // 0=déterministe, 1=créatif — 0.7 = équilibre
            );

            // Ligne D : HttpEntity = enveloppe body + headers dans un objet Spring
            HttpEntity<Map<String, Object>> request = new HttpEntity<>(body, headers);

            // Ligne E : Envoi POST vers GROQ API — retourne Map contenant la réponse JSON
            ResponseEntity<Map> response = restTemplate.postForEntity(GROQ_API_URL, request, Map.class);

            // Ligne F : Extraction du texte depuis la structure de réponse OpenAI
            // Structure JSON : { choices: [ { message: { content: "texte..." } } ] }
            List<Map<String, Object>> choices = (List<Map<String, Object>>) response.getBody().get("choices");
            Map<String, Object> message = (Map<String, Object>) choices.get(0).get("message");

            // Ligne G : On récupère le "content" et on enlève les espaces avec trim()
            return ((String) message.get("content")).trim();

        } catch (Exception e) {
            // Ligne H : Si l'API est indisponible ou token invalide → exception gérée par GlobalExceptionHandler
            throw new IllegalStateException("AI draft failed: " + e.getMessage());
        }
    }
}

def generate_synthetic_data(n: int = 400) -> pd.DataFrame:
    """Si student-mat.csv est absent, génère 400 lignes fictives réalistes."""

    np.random.seed(42)          # Graine fixe = résultats reproductibles

    data = {
        # Choix pondéré : 75% GP, 25% MS (reflète la vraie distribution UCI)
        'school': np.random.choice(['GP', 'MS'], n, p=[0.75, 0.25]),
        'age':    np.random.randint(15, 23, n),    # Entiers entre 15 et 22
        'failures': np.random.choice([0,1,2,3], n, p=[0.67,0.19,0.08,0.06]),
        # Distribution réaliste : 67% des étudiants n'ont pas échoué
        'G1': np.random.randint(3, 19, n),         # Notes 1er trimestre
        'G2': np.random.randint(3, 19, n),         # Notes 2ème trimestre
        # ... (autres colonnes)
    }
    df = pd.DataFrame(data)

    # G3 synthétique = combinaison linéaire de G1, G2, studytime, failures + bruit gaussien
    g3_base = (df['G1'] * 0.4 + df['G2'] * 0.4
               + df['studytime'] * 0.5 - df['failures'] * 2
               + np.random.normal(0, 2, n))   # Bruit gaussien (σ=2)

    df['G3'] = np.clip(g3_base.round().astype(int), 0, 20)
    # clip → force G3 dans [0,20] même si la formule dépasse
    return df

def preprocess(df: pd.DataFrame):
    df = df.copy()              # Travaille sur une copie, ne modifie pas l'original
    encoders = {}

    # Étape 1 : Encodage des colonnes catégorielles (texte → nombres)
    # LabelEncoder transforme ex: ['GP','MS'] → [0, 1]
    for col in CAT_COLS:         # CAT_COLS = ['school','sex','address','Mjob',...]
        le = LabelEncoder()
        df[col] = le.fit_transform(df[col].astype(str))
        encoders[col] = le      # Sauvegarde le mappeur pour réutilisation en inférence

    # Étape 2 : Création de la variable cible binaire
    df['pass'] = (df['G3'] >= 10).astype(int)  # 1=réussi, 0=échoué

    # Étape 3 : Sélection des features (tout sauf G3 et 'pass')
    feature_cols = [c for c in df.columns if c not in ['G3', 'pass']]

    X = df[feature_cols].values     # Matrice NumPy des features
    y = df['pass'].values           # Vecteur des labels

    # Étape 4 : Normalisation StandardScaler → moyenne=0, écart-type=1
    # Indispensable pour PCA et K-Means qui sont sensibles à l'échelle
    scaler = StandardScaler()
    X_scaled = scaler.fit_transform(X)

    return X_scaled, y, scaler, encoders, feature_cols

def train_and_save() -> dict:
    os.makedirs(MODEL_DIR, exist_ok=True)   # Crée /app/models si absent

    # Priorité : données réelles UCI. Sinon : données synthétiques
    if os.path.exists(DATA_PATH):           # DATA_PATH = /app/data/student-mat.csv
        df = pd.read_csv(DATA_PATH, sep=';')  # Dataset UCI séparé par ';'
    else:
        df = generate_synthetic_data(400)   # Fallback 400 lignes fictives

    X_scaled, y, scaler, encoders, feature_cols = preprocess(df)

    # ── ÉTAPE 1 : PCA — Réduction de dimensionnalité ──────────────────
    # n_components=0.95 → garde autant de composantes qui expliquent 95% de la variance
    # Réduit le bruit et accélère l'entraînement (ex: 32 features → ~12 composantes)
    pca = PCA(n_components=0.95, random_state=42)
    X_pca = pca.fit_transform(X_scaled)

    # ── ÉTAPE 2 : K-Means Clustering — Profils d'étudiants ───────────
    # k=3 : At-Risk / Average / High-Performing
    # n_init=10 : relance 10 fois avec des centroïdes différents → meilleure convergence
    kmeans = KMeans(n_clusters=3, random_state=42, n_init=10)
    clusters = kmeans.fit_predict(X_pca)    # Assigne chaque ligne à un cluster
    sil = silhouette_score(X_pca, clusters) # Qualité du clustering (0=mauvais, 1=parfait)

    # ── ÉTAPE 3 : Train/Test Split ────────────────────────────────────
    # test_size=0.2 → 80% train, 20% test
    # stratify=y → respecte la proportion pass/fail dans chaque split
    X_train, X_test, y_train, y_test = train_test_split(
        X_pca, y, test_size=0.2, random_state=42, stratify=y)

    # ── ÉTAPE 4 : Random Forest — Classification binaire ─────────────
    # n_estimators=100 : 100 arbres de décision — vote majoritaire
    # Plus d'arbres = plus robuste mais plus lent
    rf = RandomForestClassifier(n_estimators=100, random_state=42)
    rf.fit(X_train, y_train)

    # ── ÉTAPE 5 : Évaluation ─────────────────────────────────────────
    y_pred  = rf.predict(X_test)
    y_proba = rf.predict_proba(X_test)[:, 1]  # Proba de la classe "pass" (index 1)

    metrics = {
        "accuracy": round(float(accuracy_score(y_test, y_pred)), 4),
        # accuracy = % de bonnes prédictions
        "f1_score": round(float(f1_score(y_test, y_pred)), 4),
        # F1 = moyenne harmonique précision/rappel (mieux que accuracy pour données déséquilibrées)
        "roc_auc":  round(float(roc_auc_score(y_test, y_proba)), 4),
        # ROC-AUC = aire sous la courbe ROC (0.5=hasard, 1=parfait)
        "silhouette_score": round(float(sil), 4),
        # Silhouette = qualité du clustering (séparation entre clusters)
    }

    # ── ÉTAPE 6 : Sauvegarde des modèles avec joblib ──────────────────
    # joblib = sérialisation optimisée pour NumPy/scikit-learn (plus rapide que pickle)
    joblib.dump(scaler,       f"{MODEL_DIR}/scaler.pkl")      # Normalisation
    joblib.dump(pca,          f"{MODEL_DIR}/pca.pkl")         # Réducteur PCA
    joblib.dump(kmeans,       f"{MODEL_DIR}/kmeans.pkl")      # Modèle clustering
    joblib.dump(rf,           f"{MODEL_DIR}/rf_classifier.pkl") # Classifieur
    joblib.dump(feature_cols, f"{MODEL_DIR}/feature_cols.pkl") # Liste des features
    joblib.dump(encoders,     f"{MODEL_DIR}/encoders.pkl")    # Encodeurs catégoriels

    return metrics

def ensure_model():
    # Entraîne seulement si le modèle n'existe pas encore
    if not os.path.exists(f"{MODEL_DIR}/rf_classifier.pkl"):
        train_and_save()

    # Différence : fit_transform() recalcule la moyenne/std, transform() utilise celles de l'entraînement

    X_pca = _models["pca"].transform(X_scaled)

    return X_pca    # Vecteur prêt pour predict() ou cluster()

public void seedProfiles() {
    // Ligne 1 : Récupère uniquement les utilisateurs avec rôle STUDENT
    List<AppUser> students = userRepository.findAll().stream()
        .filter(u -> u.getRole() == Role.STUDENT)
        .toList();

    Random rng = new Random(42);    // Graine fixe → résultats reproductibles (comme en Python)
    int seeded = 0;

    for (AppUser student : students) {
        // Ligne 2 : Idempotent — ne recrée pas si déjà présent
        if (profileRepository.existsByStudentId(student.getId())) continue;

        // Ligne 3 : Génère G1 aléatoire entre 6 et 18
        int g1 = 6 + rng.nextInt(13);

        // Ligne 4 : G2 ≈ G1 ± 2 (corrélé à G1, comme dans la réalité)
        int g2 = Math.max(0, g1 + rng.nextInt(5) - 2);
        g2 = Math.min(g2, 20);          // Borne à 20 maximum

        // Ligne 5 : Construit et sauvegarde le profil
        StudentAcademicProfile profile = StudentAcademicProfile.builder()
            .student(student)
            .age(16 + rng.nextInt(6))    // 16 à 21 ans
            .g1(g1)
            .g2(g2)
            .failures(weightedFailures(rng))  // Distribution pondérée (voir dessous)
            .absences(rng.nextInt(20))   // 0 à 19 absences
            .studytime(1 + rng.nextInt(4)) // 1=<2h, 2=2-5h, 3=5-10h, 4=>10h
            .build();

        profileRepository.save(profile);
        seeded++;
    }
}

// Distribution réaliste des échecs : 65% → 0, 19% → 1, 10% → 2, 6% → 3
private int weightedFailures(Random rng) {
    int r = rng.nextInt(100);
    if (r < 65) return 0;    // La majorité des étudiants n'ont pas échoué
    if (r < 84) return 1;    // 19% ont 1 échec
    if (r < 94) return 2;    // 10% ont 2 échecs
    return 3;                // 6% ont 3 échecs
}

@Service
public class FileStorageService {

    // Dossier de stockage injecté depuis application.properties (file.upload-dir)
    @Value("${file.upload-dir}")
    private String uploadDir;

    public String storeFile(MultipartFile file) {
        try {
            // Ligne 1 : Crée un objet Path vers le dossier de destination
            Path uploadPath = Paths.get(uploadDir);

            // Ligne 2 : Si le dossier n'existe pas encore, le crée (+ parents si besoin)
            if (!Files.exists(uploadPath)) {
                Files.createDirectories(uploadPath);
            }

            // Ligne 3 : Génère un nom unique pour éviter les collisions
            // UUID = identifiant aléatoire 128 bits (ex: a3f4b2c1-...)
            // On conserve le nom original pour que l'étudiant puisse l'identifier
            String fileName = UUID.randomUUID() + "_" + file.getOriginalFilename();

            // Ligne 4 : Chemin complet = dossier + nom du fichier
            Path filePath = uploadPath.resolve(fileName);

            // Ligne 5 : Copie les octets du fichier reçu vers le disque
            // getInputStream() lit le flux binaire du fichier uploadé
            Files.copy(file.getInputStream(), filePath);

            // Ligne 6 : Retourne seulement le nom (pas le chemin complet)
            // Ce nom est stocké dans RetakeRequest.attachmentPath
            return fileName;

        } catch (IOException e) {
            throw new RuntimeException("Failed to store file: " + e.getMessage());
        }
    }
}

public RetakeRequest createRetakeFromClaim(Long claimId, RetakeRequest retakeDetails, MultipartFile attachment) {

    // Ligne 1 : Appel FEIGN → GET http://claim-service/api/claims/{claimId}
    // Eureka résout "claim-service" vers son adresse réelle (ex: 172.18.0.5:8081)
    ClaimDTO claim = claimClient.getClaimById(claimId);

    // Ligne 2 : RÈGLE 1 — Seules les réclamations PÉDAGOGIQUES peuvent générer un rattrapage
    if (!"PEDAGOGICAL".equals(claim.getType())) {
        throw new InvalidRetakeException(
            "Rule Violation: Retake requests can only be linked to claims of type 'PEDAGOGICAL'.");
    }

    // Ligne 3 : RÈGLE 2 — Anti-doublon : une seule RetakeRequest par réclamation
    if (retakeRequestRepository.existsByClaimId(claimId)) {
        throw new ClaimAlreadyLinkedException(
            "Rule Violation: A retake request is already linked to this claim.");
    }

    // Ligne 4 : RÈGLE 3 — L'admin doit avoir autorisé le rattrapage
    // (statut RETAKE_AUTHORIZED positionné par claim-service via PATCH /authorize-retake)
    if (!"RETAKE_AUTHORIZED".equals(claim.getStatus())) {
        throw new IllegalStateException(
            "Action denied: You cannot submit a retake request until the administration authorizes it.");
    }

    // Ligne 5 : Lien cross-service — on stocke l'ID de la claim, pas l'objet JPA
    retakeDetails.setClaimId(claimId);

    // Ligne 6 : Copie l'ID de l'étudiant depuis la claim (évite un 2ème appel Feign)
    if (claim.getStudent() != null) {
        retakeDetails.setStudentId(claim.getStudent().getId());
    }

    // Ligne 7 : Si un fichier est joint, le stocke sur disque via FileStorageService
    if (attachment != null && !attachment.isEmpty()) {
        retakeDetails.setAttachmentPath(fileStorageService.storeFile(attachment));
    }

    // Ligne 8 : Sauvegarde la RetakeRequest dans retake_db
    RetakeRequest saved = retakeRequestRepository.save(retakeDetails);

    // Ligne 9 : Notifie claim-service du lien créé (2ème appel Feign)
    // PUT http://claim-service/api/claims/{claimId}/link-retake/{saved.getId()}
    // → claim-service stocke retakeRequestId dans la Claim pour le lien bidirectionnel
    claimClient.linkRetakeRequest(claimId, saved.getId());

    return saved;
}
Pourquoi 2 appels Feign dans cette seule méthode ?
  1. claimClient.getClaimById() → Vérifier les règles métier AVANT de créer
  2. claimClient.linkRetakeRequest() → Notifier claim-service APRÈS la création pour synchroniser le lien
Cette double synchronisation garantit la cohérence des données entre les deux bases (claim_db et retake_db).
